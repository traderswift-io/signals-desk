# Signals Desk executor

This is the TraderSwift demo desk. The Signals service is private; obtain a subscriber token from the signal publisher. See [SETUP.md](../SETUP.md) for the five-bot setup, UTC routines and delegate-policy registration with Signer.

Chain verification runs once at the Desk Lead's intake through `desk_anchor_verify`, which journals a pass bound to the envelope's payload hash; with `resident: false`, the routine Executor `run` and the `desk_ticket` gate and size previews refuse `anchor_not_verified` without a matching record; the other seats act on the envelope the Lead routed; the resident signal consumer does not run the verifier.

The Signals service anchors nothing on chain yet (`receipt: null`), so today the verifier refuses every signal on this branch until anchors are published.

Based on HyperGrok Trading Desk. The existing [MIT license](../LICENSE) remains unchanged. This component adds policy-authorized execution through an ed25519 delegate, a position sizer, a local policy mirror, and software exits. It does not use a venue signing key.

Python 3.11 or newer on Linux is required, with `aiohttp`, `PyNaCl`, and `redis`. Scenario checks also require `redis-server` on the command search path.

## Commands

From the repository root, after supplying a private config JSON:

```sh
python3 -m desk.desk_keygen desk/config.json
python3 -m desk.desk_signal_consumer desk/config.json
python3 -m desk.desk_wake desk/config.json
python3 -m desk.desk_executor --config desk/config.json --close-ms <close_ms> wake
python3 -m desk.desk_executor --config desk/config.json --close-ms <close_ms> run signal.json
python3 -m desk.desk_executor --config desk/config.json --close-ms <close_ms> cancel SIGNAL_ID
python3 -m desk.desk_ticket --config desk/config.json size signal.json
python3 -m desk.desk_ticket --config desk/config.json --close-ms <close_ms> gate signal.json
python3 -m desk.desk_ticket --config desk/config.json review SIGNAL_ID
python3 -m desk.desk_anchor_verify desk/config.json envelope.json
```

For routine commands, replace `<close_ms>` with the integer printed in the initial `desk_wake` JSON. Carry it unchanged through maintenance, gate and submission; resident commands do not require it. Cancel remains available without a close for withdrawals. Missing or outdated closes refuse `stale_wake_close`, including a boundary crossed during maintenance candle reads, prepare or oracle reads. Maintenance rechecks after the candle read before recording or dispatching a new invalidation cancellation. End a stale handoff and wait for a new wake.

The default executor config path is `desk/config.json`, so `python3 -m desk.desk_executor cancel SIGNAL_ID` also works. Key generation runs once on the executor machine, prints only the public key, creates its directory with mode 0700 and its file with mode 0600, and refuses to replace any existing destination. Storage writers create journal, lock and delivery files with mode 0600 and their directories with mode 0700. Startup tightens existing storage and key directories owned by the desk user to 0700 and files to 0600, logging each old and new mode with a path relative to the config. It refuses with `insecure_permissions` if ownership differs or tightening fails. Use dedicated private directories for these paths. Protect the config and local control socket directory with owner-only permissions. Config, key, record, and socket paths are operator-configured; relative paths resolve from the working directory.

The ticket CLI also defaults to `desk/config.json` and prints one JSON object. `size` prints the existing sizer's decimal strings or its refusal with the numbers. `gate` prints `status: PASS` with `sizing` and an unsigned `intent` preview, or `refused` with the same policy reason as the executor. Both use the executor's shared entry preview, including venue price rounding and nonresident bracket construction. These commands only read public Info and local files; they never prepare, send, or append records. They never load the delegate seed or need door credentials. Size needs no delegate identity only while no intent rows require budget evaluation; a valid shared journal with intents requires the delegate public key for that evaluation. Gate requires `delegate_public_key` (the public hex printed by keygen), the issued `key_ref`, and reads the Executor's journal for the same daily budget. For resident previews, a missing journal counts as nothing signed today; routine size and gate previews require a matching `anchor_verified` record; Signer still enforces the daily cap; a missing or malformed public key refuses `invalid_delegate_public_key`. Read-only seat configs retain the example fields, with unused credential and seed fields left as placeholders. Keep the policy, public identity and journal current; a stale copy cannot establish current budget availability. A gate PASS describes the policy mirror; execution still checks candle eligibility, account occupancy and resident watcher readiness. `review` reads the recorded Reviewer object, including signal entry, fill, slippage and the recorded stop mode; it returns `unknown_signal_id` or `review_unavailable` when absent and never creates a review.

`desk_signal_consumer.py` does not verify anchors; its resident path is unchanged. The consumer uses blocking stream reads and persists the last processed stream id. A Redis connection failure is recorded, cancels active tickets through the normal reduce-only closeout, and stops the consumer; restart resumes from the saved cursor. It holds an exclusive record lock. A cancel command uses the running executor's local control socket; when no executor is running, it acquires that lock and reconciles outstanding tickets before cancellation. Resident startup recovery closes outstanding exposure and never resends an entry. Routine startup reconciles existing brackets without closing protected positions or resending entries. Use a single configured record for a follower account and keep it across restarts.

Only the resident consumer sends `POST /v1/deliveries`, with the stream entry ID as `event_id`. Grok seats make no delivery report: the service records each signal returned by their GET for that desk's token. Assign one subscriber token to one desk. Set `signals_url`, `subscriber_token_file` (read once at startup), `signals_access_client_id` and `signals_access_client_secret` for resident delivery reports. Reporting is off when the `signals_url` key is absent. If the URL is set but the token file is unreadable, empty or multi-line, a sanitized `deliveries_disabled` reason is recorded and reporting stays off; recovery and trading continue. Invalid URLs or missing delivery credentials have the same behavior. Fix the configuration and restart to enable reporting; entries consumed while reporting is disabled are not queued.

The consumer waits only for the queued row to be fsynced in the delivery file before writing its cursor; it never waits for a POST. Delivery rows go to `<record_path>.deliveries.jsonl` with its own file lock. Delivery writes run through `asyncio.to_thread` and never hold the trading journal lock. Pending state is reconstructed once at startup from the delivery file alone and maintained in memory; there is no migration from trading journal rows. Existing trading code and its synchronous journal I/O are unchanged.

Startup opens or creates the delivery store under its exclusive lock, fsyncs the file and its parent directory, and only then enables reporting. This directory sync also runs on existing files so a failed earlier creation sync can be retried. Later appends require the file to exist; they never recreate it silently. Any future replacement must fsync the parent directory before a cursor can depend on the replacement. With reporting enabled, failure to persist a queued row prevents cursor advancement.

Under that same startup lock, a final record without a terminating newline or with unparseable JSON is copied before truncating to the preceding complete newline-terminated record. The removed bytes are appended verbatim to `<record_path>.deliveries.jsonl.torn` with mode 0600; the copy and its parent directory are fsynced before truncation. The directory sync runs even for an existing copy, covering a failed earlier creation sync. If copying or either sync fails, the delivery file stays intact and reporting is disabled. The truncation is fsynced, then one `delivery_tail_truncated` row with the `removed_bytes` count is appended and fsynced. Complete queued identities survive. Corrupt interior records are never skipped or repaired; reporting stays off, while recovery and trading continue. A corrupt or unavailable store records `deliveries_disabled` through the trading journal's diagnostic path, with reason `delivery_store_corrupt` or `delivery_store_unavailable` and only the exception type, without exception text. A general guard covers all delivery preparation, including the delivery-state read; unexpected exceptions disable reporting with only their type as the reason and still allow recovery. If that diagnostic cannot be persisted, a fixed loop diagnostic is emitted and delivery initialization still returns to trading recovery. Other delivery diagnostics stay in the delivery file. Fix the store and restart to enable reporting; as with invalid configuration, entries consumed while reporting is disabled advance the trading cursor normally and are not queued for later reports.

Retain and restore the trading journal and delivery file together. Retain any `.torn` copy for inspection; it is not replayed as delivery state. A failed repair may append the same tail again on restart.

One coalescing worker runs a sweep after startup recovery and on stream entries, including malformed entries. Each sweep retries at most ten eligible pending reports, oldest first by first insertion, plus the latest fresh report if present. Entries arriving during a sweep request another sweep; intermediate fresh entries remain in the pending backlog. There is no retry timer: future deadlines and idle backlogs wait for another stream entry or restart. A 429 stops the sweep immediately and persists a subscriber-wide cooldown, leaving fresh reports queued. Retry-After eligibility and deadlines use the local wall clock, never stream timestamps. All failures back off: transport errors, timeouts, non-2xx responses, bad bodies (including decoding exceptions and missing acknowledgement), and 429 use wall-clock delays starting at 5 seconds and doubling up to 15 minutes; Retry-After can extend that delay. After 20 failed attempts, `delivery_abandoned` is terminal across restarts and replays. Each completed attempt writes one outcome row, without a `sending` row. Unexpected task errors record only their exception type as `delivery_error`; filesystem failures are supervised separately from HTTP attempt failures.

Shutdown cancels delivery work, gathers task outcomes, and waits at most 5 seconds for in-flight delivery persistence. It then stops waiting and leaves the on-disk row as it is; complete queued or pending rows are eligible for retry after startup tail recovery when the store is usable. A filesystem operation running in a thread cannot be forcibly cancelled by asyncio and may outlive this budget. Configure `UMask=0077` and `TimeoutStopSec=15` in the resident service unit's `[Service]` section: a filesystem stuck below the application is ended by the service manager's stop timeout. Keep the normal service-manager termination of the entire service process group enabled before allowing a restart.

Acknowledged stream IDs can be reported again on replay, and ambiguous responses can cause repeat POSTs; service idempotency is required. Trading deduplication remains separate. Delivery-file and `.torn` copy growth remain unbounded; retention/compaction and an automatic drain of idle delivery backlogs are not implemented.

```sh
make check
```

Ticket scenarios compare the `size` and `gate` CLI output against the executor's own records for sizing failures, policy refusals, daily spending and rounded buy/sell entries. The budget identity scenarios compare clean journals against twelve conflicting request-ID variants before and after a genuine verification pass, through size, gate, routine run and direct submit. Symbols match case-insensitively across the main and configured builder universes. No match refuses `symbol_unmapped`; multiple matches refuse `symbol_ambiguous`. ## Anchor verifier protocol

Set `record_path` to the same current trading journal for the Desk Lead, Executor, Position Sizer and Risk Gate. Give the Lead append access for verifier passes, the Executor its existing journal access, and the preview seats read access. A separate workspace or stale journal copy cannot provide a new pass to another seat. Protect journal integrity with workspace permissions; the gate trusts these local records.

Run `python3 -m desk.desk_anchor_verify desk/config.json <envelope.json>` from the checkout root before ticket posting or handoff. Validation stops at the first refusal: fully parse and validate config before opening the envelope; parse the envelope and validate its identity; canonicalize and hash its payload; then read charter, provider (including its address pin), and anchor (including its hash). No chain writes, redirects, retries or sleeps occur.

Config must be an object with `chain_url`, `provider_id` and `provider_address`; `record_path` must name the writable shared journal for a pass to complete. The base must use HTTPS with a host, an empty or `/` path, and no userinfo, query or fragment, including empty `?` or `#` suffixes. Whitespace, control characters, backslashes and malformed ports are refused; endpoint paths replace parsed URL components. Use `https://chain.traderswift.io`. The pinned address must be a nonempty string and is compared exactly, without trimming or case folding. Both provider and signal IDs must match `^[A-Za-z0-9._:-]{1,128}$` in full, excluding `.` and `..`. `request_timeout_seconds` defaults to 10 and must be a finite JSON number, not a boolean or string, with `0 < x <= 60`.

Config, envelope and chain JSON reject duplicate object keys and bare `NaN`, `Infinity` and `-Infinity` at every depth. Unreadable files, malformed local JSON or file decoding, and input recursion failures yield `invalid_input`. The envelope and its `payload` must be objects with a valid string `payload.signal_id`, checked before canonicalization. Canonicalization supports objects with string keys sorted by UTF-16 code units, arrays, valid Unicode scalar strings, booleans, null and integers with absolute value at most 9007199254740991. An integer of more than 4,300 digits hits the JSON parser's digit limit first and refuses earlier: `invalid_input` in a local config or envelope file, `chain_unavailable` in a chain body. All floats, unsupported payload values and unpaired surrogates in payload strings or keys yield `payload_not_canonical`; payload recursion yields `invalid_input`. Whitespace and key order are normalized without Unicode normalization. Escaped valid surrogate pairs decode to supported scalar strings. Unused local fields outside the payload are not recursively Unicode-validated.

The three GET paths, relative to the configured base, are `/network/v1/charter/signals`, `/network/v1/provider/signals/<provider_id>`, and `/network/v1/anchor/signals/signal/<signal_id>/<provider_id>`. Both provider path segments use the config pin; the signal segment uses the validated payload ID. Each response status is checked before its body: 429 or any status >=500 yields `chain_unavailable`; every other non-200, including redirects, yields that read's missing refusal. Only 200 bodies are decoded, with aiohttp JSON MIME checking (including `application/*+json`). Invalid JSON, duplicate keys, non-JSON constants, charset/text decoding errors, invalid Unicode scalar strings or keys at any depth, decoding/validation recursion, or a non-object body yields `chain_unavailable`. Chain numbers are not subject to the payload's restricted numeric subset. Only top-level fields are inspected for veto, address and hash; records are not unwrapped.

The result is `pass` or exactly one of these twelve refusals. Each condition applies only after preceding checks have succeeded:

| Refusal | Condition |
| --- | --- |
| `invalid_input` | Unreadable or malformed config/envelope file, duplicate keys, non-JSON constants, invalid config, or input/payload recursion. Config validation precedes envelope access; failure to persist a successful verification in the configured journal also refuses. |
| `invalid_envelope` | Envelope or payload is not an object, or `payload.signal_id` is missing or violates the ID grammar. |
| `payload_not_canonical` | Payload contains a float, unsafe integer, unsupported type, non-string key or invalid Unicode after identity validation. |
| `chain_unavailable` | Connection, TLS, timeout or other aiohttp client error; 429 or any status >=500; invalid 200 body/MIME/charset/Unicode as above; or recursion during chain processing. |
| `charter_missing` | Charter status is non-200 and below 500, except 429. |
| `charter_vetoed` | Decoded charter object's `vetoed` is missing or anything other than literal JSON `false`. |
| `provider_missing` | Provider status is non-200 and below 500, except 429. |
| `provider_vetoed` | Decoded provider object's `vetoed` is missing or anything other than literal JSON `false`. |
| `provider_address_mismatch` | After provider veto checking, `provider_address` is absent, not a nonempty string, or not exactly equal to the config pin. |
| `anchor_missing` | Anchor status is non-200 and below 500, except 429. |
| `anchor_vetoed` | Decoded anchor object's `vetoed` is missing or anything other than literal JSON `false`. |
| `hash_mismatch` | After anchor veto checking, `segment_hash` is absent or not exactly the lowercase SHA-256 hex of the canonical payload's UTF-8 bytes. |

The CLI prints exactly two lines: JSON metadata with `signal_id` (validated ID or null) and `reads` (received HTTP statuses in order), then `VERIFY | <validated ID or -> | <result>`. Only the VERIFY line carries the result; no raw exception text is a result. Exit status is 0 only for `pass`, otherwise 1. After all three reads pass, the verifier appends and syncs an `anchor_verified` record containing `signal_id` and `payload_hash`, the lowercase SHA-256 of the JCS payload; a missing journal path or failed journal write refuses `invalid_input`. A pass requires all three reads, each with literal `vetoed: false`, the exact provider address and exact recomputed payload hash. Envelope, receipt and stream hashes are ignored. Require both the printed pass and exit 0 before routing; anything else blocks processing. Missing anchors remain pending until the next routine.

Routine submission and size/gate previews recompute the canonical payload hash and require an `anchor_verified` record with the same `signal_id` and `payload_hash`. They make no chain reads. A missing, unreadable or malformed journal, a changed payload or no matching record refuses `anchor_not_verified`; formatting and object key order do not change the hash. The record binds the payload, not outer envelope or receipt fields, and does not establish continuing chain status. The explicit cancel command and maintenance of existing tickets remain available under their existing checks.

The journal is trusted for well-formed, consistent rows written with the desk's file permissions. Corruption checks fail closed for torn or partial lines, malformed values, duplicate keys, non-Decimal numeric values and rows that contradict intent, reply, outcome or signal content for the same identity, including terminal tickets. Integer numbers remain supported. The code creates journal, lock and delivery files with mode 0600 and their directories, including newly created parents, with mode 0700. At startup it tightens existing storage, its managed parent directories and the key directory owned by the desk user to those modes, logging each changed path relative to the config with its old and new modes. It then checks permissions and refuses with `insecure_permissions` and a config-relative path if ownership differs or tightening fails; symbolic links are refused. Subsequent opens enforce owner-only permissions. Key generation also prepares its directory this way, creates its file with mode 0600 and refuses to replace an existing destination. Protect the desk's code and config with the same owner-only access. A forged row that is valid and consistent is outside this threat model: journal protection depends on these file permissions and the owner remaining trusted. These checks do not authenticate journal authors.

Any unreadable or implausible journal row makes size, gate and routine run refuse `anchor_not_verified` before any coordinator prepare or intent call. Every record must end with a newline (LF); appends also refuse an unterminated tail instead of completing it accidentally; an unterminated final JSON object, truncated record, blank line or whitespace-only tail is refused. Every line must decode to a record object with a nonempty string `event` and a nonnegative integer `timestamp` (not a boolean). The shared strict JSON decoder rejects duplicate object keys at any nesting depth and non-JSON constants (`NaN`, `Infinity`, `-Infinity`) before field validation. The reader checks every row, including rows after a matching pass, and limits nesting to 32 levels. It validates the fields used by recovery, deduplication and budget reads: state keys contain three strings; state signals contain the required identifiers, side, timing and numeric levels; intents contain a request ID and kind, with typed asset, side, size, price and order fields required for orders and bracket entries. Brackets require a typed stop and, when present, a typed take-profit leg, including boolean direction and protection flags, decimal strings for size and prices, and the matching asset, size and trigger kind. Null or array-valued legs are malformed. A central event-to-field table checks every recorded field, including refusal signal IDs, rearm intents, state metadata, replies, outcomes and execution and delivery diagnostics. Unknown events or fields refuse. An AST scenario checks production writer calls, forwarding functions and expanded dictionaries against that table; adding an unlisted event or field fails the check. Monetary fields emitted as strings retain that exact type; integer timing fields reject booleans. Cancels require an asset, asset index and integer order reference (`oid`); scheduled cancels require an integer `time_ms`. Reusing a request ID with different intent content makes the whole journal malformed, before or after a matching pass. Identical intent resends count the earliest reservation once; cancelling an order never releases its spent budget. Replies must follow a recorded intent and cannot predate its reservation. Repeated replies must preserve all earlier outcome fields, including signature fields when present; conflicting replies or unknown request IDs make the whole journal malformed. Consistent confirmations can add fields or extend the accounting period, but cannot reduce spent budget. The writer may retry a rate-limited cancel or reduce-only exit after recording another identical intent. Replies and bracket outcomes allow boolean or null `signed` values; an `ambiguous` field, when present, must be a boolean. String substitutes for either flag are malformed. Before returning any rows, the shared reader checks request and ticket identities, unchanged state signals, and outcome agreement with the recorded intent and reply, including histories whose tickets are already terminal. An outcome's complete intent copy must equal the recorded intent, including every nested leg field and the delegate signature; its signed and ambiguous flags must agree with its reply. The writer retains that exact signed intent copy. Older identified outcomes that omitted the signature fail closed and require operator reconciliation; the desk does not rewrite historical evidence. A missing reply or a well-formed ambiguous reply with missing or null `signed` keeps its reservation across UTC days. An explicit unsigned reply releases only an unsigned reservation; state, outcome and review records never release spent budget. The reader and budget share execution-evidence checks: reply flags must agree with retained venue statuses and ambiguity reasons; an unsigned entry reply contradicting later entry orders, fills, position observations, filled states, reviews or signed exits makes the journal malformed, including resident IOC history. Ambiguous replies may retain reconciled exposure and remain reserved. State transitions must follow the state machine, and entry completion cannot revert. An entry_done flag is accepted only after a recorded entry fill or position observation confirming completion, or a successful cancellation of the recorded entry order followed by reconciliation confirming its absence. Changing the pre-dispatch sent flag alone therefore refuses the journal. Resident size/gate previews and submission also return anchor_not_verified for journal corruption before coordinator calls; they do not verify chain anchors.

Recovery may mark a flat ticket `exited` from a `bracket_result` only when the row carries the request ID of that ticket's recorded bracket intent and its `signed` and `ambiguous` values agree with the recorded reply, with `signed: true` and no ambiguity. An omitted `ambiguous` field means false, as in successful writer replies. A legacy row with no request ID and no intent copy leaves the ticket unresolved and blocks new entries with `account_busy`; a contradictory identified outcome makes the shared reader refuse the journal with `anchor_not_verified` before budget use or recovery; recovery also requires recorded fill or confirmed cancellation evidence for the entry-completion path and never exits an unresolved flat ticket on entry_done alone.

For a reservation retained because a reply is missing or null-signed, reconcile the entry against venue fills through the supported routine command `python3 -m desk.desk_executor --config desk/config.json --close-ms <close_ms> wake`, using the close from `desk_wake`. Recovery and maintenance call `desk_executor.reconcile`, which reads orders, fills and account state and records the observations through `append_record`; confirmed ticket transitions use `set_state`. This records the observed outcome through the desk's own writer. There is no operator-facing command to replace a missing or null-signed reply with a definite unsigned result. Reconciliation can manage confirmed exposure and complete a ticket, but does not rewrite that reply or release its daily reservation; the reservation can remain across days. Keep the journal intact and do not replay the entry or append a hand-written release.

Journal numbers are read exactly as Decimal or integer values, without binary-float conversion; out-of-range or over-precise numbers make the gate refuse `anchor_not_verified`. Integer literals are limited to 4,300 digits before conversion. Journal numbers must be finite, have magnitude below `10**15`, at most 28 coefficient digits, and a stored exponent between -28 and 14; nonzero values also need an adjusted exponent in that range. Numeric text is limited to 64 characters. Prices and sizes must be positive; integer timing and index fields must be nonnegative, and booleans cannot stand in for numbers. Negative zero is rejected; integer fields also reject fractional or exponent notation, including `1E+2`. A float reaching journal validation is malformed. The journal writer stores Decimal values and float diagnostics as decimal strings, retaining integer timestamps. These limits cover numeric JSON values and the numeric strings consumed by recovery and budget accounting. Before accepting a pass, the anchor gate also computes journal budget reservations. A shared exception boundary returns `anchor_not_verified` without exception text for any exception while checking the journal or using it for routine deduplication, budget accounting or recovery.

## Execution and records

Routine-driven bots set `resident: false`. An eligible signal submits exactly one `bracket`: a GTC entry at the signal entry, a resting stop at `levels.stop`, and a take-profit at `levels.target` when present. Venue precision rounding uses the existing price helper. Legs have the same size as the existing sizer’s entry, opposite direction, `reduce_only: true`, and `is_market: true`; their limit prices bound slippage. A signer refusal records `bracket_refused` with the unchanged reason and sends no plain entry. Reviewer records say `stop: bracket`.

The UTC routine runs at :01, :16, :31 and :46. Its first command, `desk_wake`, makes two public Info reads per mapped market for the vault and emits a JSON object and a `WAKE` line. On `no`, the routine ends without posting. It uses `frontendOpenOrders` to distinguish resting entries from reduce-only triggers and `clearinghouseState` for positions, including mapped builder markets. Inside mapped active hours it wakes for an entry, a position, or the :00 close’s hourly signal check. It never reads the Signals service or a delegate seed. Failures produce `wake_unavailable` and `no`.

On `yes`, run the Executor’s `wake` command before routing signals. It reconciles existing tickets and cancels resting entries whose `reply_by` has expired or whose invalidation level has closed through. Maintenance, gate and submission use the explicit wake `close_ms` for the closed candle from `candleSnapshot`; missing candles fail closed. Submission checks that this close is still the last fully closed 15m bar immediately before sending and never substitutes a newer bar. A numeric `levels.invalidation`, if present, overrides `levels.stop`; the required prose `invalidation` remains descriptive. Comparison is inclusive: at or below for longs, at or above for shorts. A publication newer than the last close waits for a later close without being claimed. New entries and gate previews use the same guard. Repeated signals cannot create a second entry.

Active UTC intervals include their start and exclude their end, applied to the candle close timestamp and configured weekday range. Split overnight sessions at midnight; there is no implicit holiday or daylight-time calendar. Routine `run` first requires a matching verification record; eligible `run` and `wake` commands exit after one reconciliation pass, without starting a websocket, control server or background timer. Expiry or invalidation cancels only the unfilled entry remainder; a partial position retains its protective legs. Confirmed entry cancellation is persisted in the journal. Reconciliation also persists entry completion when no resting entry remains and the position is nonzero. Once a later pass sees the position flat, remaining legs are cleaned up, including after a stop closes a fully filled position, across restart and without an expiry or invalidation condition. Refused cancellations are recorded and retried on the next pass; the ticket occupies the account until all legs are confirmed gone. Existing positions close through the bracket, unless the signal is withdrawn with the existing cancel command or cancel envelope. Ambiguous outcomes remain held and never cause an entry replay.

Brackets need a Signer release that signs the bracket kind; until then the signer refuses the kind and the desk records `bracket_refused`. A venue-side scheduled cancel on the account can remove resting orders, stop legs included, between routine runs. This fork does not recommend live use until Signer documents how a bracket's stop survives it. Venue errors on any bracket leg are recorded as unresolved; a successful signature alone is not proof of protective orders.

The sizer uses quantity = risk fraction × equity / absolute entry-to-stop distance and rounds quantity down to the venue size precision. Maintenance rates and cumulative tier deductions determine the cross-margin liquidation estimate. The stop needs at least 0.25% of entry price between it and liquidation. Only a dedicated account that is initially flat, with no open orders, in the configured markets (the signal's market and the main and configured builder DEXs) is accepted; one active ticket occupies the account.

Resident entries are IOC at the signal entry rounded to venue price precision, up for buys and down for sells. The gate and intent record the rounded price; the original signal entry remains available for review. An IOC with a confirmed unfilled outcome finishes as `not_filled`; it is never retried. Both websocket subscriptions must acknowledge before submission. Stops and targets are software-triggered reduce-only IOC orders. The first exit round uses the trigger level plus the configured fractional band and cached size precision. After each partial or unfilled round, the next round reads the current mark and applies the band to it. Exits without a trigger read the current mark from the first round. No resting stop or target is created. The reviewer records `stop: software`, entry/fill prices, directional slippage and whether the stop traded.

Every `trades` and `userFills` message and every coordinator reply checks policy expiry: an open position exits reduce-only when now is at or past `policy.expires_at - 60` seconds. `reply_by` gates entry only. An IOC entry has no deadline callback. Websocket heartbeat/read timeout marks the watcher dead and attempts reconnection; it never decides an expiry exit. A successful reconnect emits `watcher_restarted`; the Executor reconciles orders, fills and position through Info, then checks the current mark against stop and target and checks policy expiry. Failed reconnection applies the dead-watcher rule and flattens reduce-only. There is no periodic polling loop. Successful closeout depends on venue availability and fills; an expired or revoked policy prevents further orders.

Trade batches check the cached position without Info requests until closeout is triggered. Pending batches for a ticket append all trades to one queued event, including while waiting for the operation lock, so a later recovery cannot hide a stop wick. Fills, coordinator replies and watcher restarts reconcile. Stop and target closeouts use the cached position for the first round; cancel, expiry, watcher-dead and restart-recovery closeouts reconcile before sending. Every closeout reconciles after each round.

The coordinator contract uses canonical signed envelopes, coordinator-owned nonces, validated signed schedule-cancel rearm, and at most one fresh prepare after a stale-nonce refusal. Request pacing enforces 60 door requests per minute. A rate-limited entry is refused; an exit honors Retry-After or exponential backoff. Missing rearm is refused. Neither service-token credentials nor the seed are journaled.

The state store records `claimed`, `sent`, `filled`, `refused`, `not_filled` and `exited`. `refused`, `not_filled` and `exited` are terminal and skipped on recovery.

The journal syncs before submission and records every send, coordinator reply, both observed oracle prices and their local observation timestamps, transitions, reconciliation and review. A UTC-day budget counts the first order or bracket entry size once per request ID, excludes protective legs, includes failed signed rounds and conservatively reserves ambiguous sends. Identical intents retain the original size and earliest reservation date; conflicting intents, replies or copied outcomes refuse the whole journal, including terminal-ticket history. Signed spending is counted from reservation through the latest consistent confirmation day; a reservation without a definite signed outcome continues into each new UTC day. Later intent, reply, outcome, state or review rows cannot reduce a recorded signed reservation. Cancels change pending orders, never spent budget, so a cancelled entry still counts. Explicit unsigned replies release only unsigned reservations. A completed outcome may free the pending ticket slot without freeing spent budget, subject to the bracket-result and earlier entry-completion evidence checks above during recovery. A changed reply cannot discard spending contradicted by retained entry execution evidence. Redelivery never creates another entry, even with a different publisher label for the same follower and signal id.

Before each exit or cancel send, the two oracle observations run concurrently with one attempt per source and a 0.5-second HTTP timeout each. A failed source records null price and timestamp plus its error, and the send continues through the policy gate. Entries refuse failed price reads; an unmapped Binance symbol is recorded without refusing. A stop or target closeout with no cached resting orders makes three HTTP calls before its first intent: one prepare, one venue oracle read and one mapped Binance read, with no reconciliation reads. Other closeout reasons retain the three initial reconciliation reads. An exit without a trigger adds one mark read; an unmapped Binance symbol removes one ticker call.

After an ambiguous send, open orders, fills and account positions are reconciled before further execution. Confirmed exposure is managed; an unresolved entry remains held and blocks new entries. Within the journal trust model above, a corrupt journal, including contradictory terminal outcomes, malformed refusal identities, conflicting replies, replies preceding their intent or replies for unknown request IDs, fails closed before routine entry coordinator calls. Consistent resends preserve spending; unsigned refusals and completed-ticket releases retain their separate roles. These conditions require reconciliation rather than deleting the record or replaying the signal.

## Reusing the delegate client

`signer_delegate_client.py` imports only the standard library, aiohttp and PyNaCl. It works as `desk.signer_delegate_client` or as a standalone module on the import path. It requires no desk state, signal, policy or record module.

Use `create_client(config, session, key=None)` with a reusable aiohttp session and an optional PyNaCl signing key; otherwise the key is loaded from `delegate_key_file`. The client config uses coordinator/Info URLs, Access credentials, key reference, vault/account addresses, optional request timeout and `builder_dexs`. `refresh_meta(client)` returns the combined universe; `resolve_symbol(symbol, meta)` returns canonical `asset` and `asset_index`. `order_fields(asset, size, price, is_buy, reduce_only=False)` and `cancel_fields(asset, order_id)` build IOC and cancel fields without a signal object. `bracket_fields(asset, size, entry_price, is_buy, stop_trigger, stop_limit, take_profit_trigger=None, take_profit_limit=None)` builds normalized GTC bracket fields and refuses wrong-side or out-of-band triggers locally. Coordinator refusal reasons pass through unchanged.

`await run_round(client, fields, before_send=None, validate_rearm=None, on_event=None)` serializes rounds. `before_send(body)` is an async callback run before every intent dispatch, including resends; return a refusal string or None. `validate_rearm(rearm)` is a synchronous extra policy check, returning a refusal string or None. `on_event(event, **values)` is synchronous and receives prepare replies, intent replies, backoffs and nonce retries. The caller supplies policy, authorization and persistence through these callbacks; the client always checks the rearm contract itself.

An ambiguous intent triggers Info reconciliation while the round lock is held and returns a `reconciliation` snapshot containing asset orders, fills and account state. No ambiguous intent is resent. Failed Info reconciliation propagates to the caller, which must retain the unresolved operation. The desk adapter consumes the snapshot and persists ticket transitions separately. Builder market contexts, account state and open orders are read with the resolved DEX; fills are filtered by canonical coin name.

## Bracket wire references

The bracket wire shape is an `order` action with `grouping: normalTpsl`: GTC entry first, reduce-only stop next, optional take-profit last. The desk sends bracket fields to the coordinator; Signer builds and serializes the venue action. The scenario wire fixture checks that translation.

The [Hyperliquid exchange-endpoint documentation](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/exchange-endpoint) describes order fields `a`, `b`, `p`, `s`, `r`, `t`, optional `c`, and trigger fields `isMarket`, `triggerPx`, `tpsl`. The [Python SDK signing.py](https://github.com/hyperliquid-dex/hyperliquid-python-sdk/blob/master/hyperliquid/utils/signing.py) shows their wire ordering, the `type`, `orders`, `grouping` wrapper and numeric formatting. The desk normalizes Decimal strings; Signer owns final serialization and digest validation. The 50% band, direction and size restrictions are Signer policy, not venue guarantees. The scheduled-cancel limitation above still applies.
